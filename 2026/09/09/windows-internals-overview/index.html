Windows Internals：使用者模式與核心邊界

從 PE 載入、Process/Thread、虛擬記憶體到 syscall 分派，建立可用於逆向與除錯的 Windows 執行模型。

#Windows Internals#Reverse Engineering#PE

為什麼要讀 Windows Internals？

做逆向工程、事件調查、驅動開發或效能診斷時，只知道 Win32 API 的名稱並不夠。真正有用的是能把一個行為沿著系統層次往下追：哪個 process 發起、哪條 thread 執行、哪段 virtual memory 被存取、哪個 kernel object 被引用，最後由哪個 system service 完成。

Microsoft 對 process 的定義不只是「一個正在執行的程式」：它同時包含私有虛擬位址空間、可執行程式碼、開啟的 object handle、安全權杖、環境資訊、優先權與至少一條 thread。真正被 scheduler 排程的是 thread，而不是 process。

先建立五張彼此相連的地圖：

  1. 執行地圖：Process、Thread、Job Object、Token。
  2. 載入地圖：PE、Section、Loader、PEB/TEB、模組鏈。
  3. 記憶體地圖：Virtual Address、VAD、Page Table、Working Set。
  4. 資源地圖：Handle Table、Object Manager、Namespace。
  5. 邊界地圖：Win32 API、Native API、System Call、Kernel Service。
Tip

User mode / kernel mode 是 CPU privilege boundary，不等於「一般 API／進階 API」。大量高階功能仍在 user mode 完成；只有需要受保護資源或核心服務時才跨越邊界。

一次 API 呼叫實際經過哪些層？

以檔案開啟為例，應用程式可能呼叫 CreateFileW。Win32 層先整理參數，再進入 ntdll.dll 的 Native API，最後經 system call 切換到 kernel mode。Kernel 端的 Object Manager 與 I/O Manager 解析名稱、檢查權限、建立或引用 file object，再把要求送往 file-system 與 storage stack。

這條鏈帶來三個分析原則：

  • API 名稱不等於最終行為。 不同 Win32 API 可能收斂到同一組 Native API。
  • User-mode hook 只看得到部分路徑。 直接呼叫 Native API 會改變觀測結果。
  • Kernel telemetry 也不是完整真相。 ETW、minifilter、callback 與 EDR sensor 各自只覆蓋特定層次，必須交叉驗證。

PEB、TEB 與 Loader 狀態

PEB 保存 process 級 user-mode 狀態，包括 loader data、process parameters 與 heap 資訊；TEB 保存 thread 級狀態，包括 stack boundary、TLS、last-error 與 exception 相關欄位。

結構範圍常見用途注意事項
PEBProcess模組鏈、命令列、環境、process heapUser mode 可寫，不能單獨視為可信安全證據
TEBThreadStackBase/StackLimit、TLS、LastErrorValue每條 thread 各有一份
EPROCESSKernelToken、handle table、address-space metadataLayout 隨版本變動，應以 symbols 解析
ETHREAD / KTHREADKernelWait、priority、kernel stack不要把固定 offset 套到其他 build

在 x64 Windows，GS base 指向目前 thread 的 TEB，而 gs:[0x60] 是 TEB 內保存的 PEB 指標。這句話常被簡寫成「gs:[0x60] 是 PEB」，但兩者層次不同。x86 通常透過 FS 存取 TEB；WOW64 還同時牽涉 32-bit 與 64-bit 執行環境。

Warning

PEB/TEB 是半公開的內部實作。逆向時可以觀察，產品程式不應依賴未文件化欄位或固定 offset。Kernel 結構更必須搭配正確的 Microsoft symbol 與目標 build。

Loader list 為什麼不能當唯一答案？

正常 DLL 由 loader 建立 module record，並出現在 PEB loader lists。可是 manual mapping、損壞的 loader state、已卸載但殘留的 mapping，或刻意 unlink 都可能造成「記憶體中有 executable image，但 loader list 沒有它」。因此至少要交叉比對：

  • PEB loader list 與工具列出的 modules。
  • VAD / memory map 中的 MEM_IMAGE、MEM_MAPPED、MEM_PRIVATE。
  • PE header、section alignment 與 executable pages。
  • Thread start address、stack return address是否落入未命名區域。

虛擬記憶體：Address Space、VAD 與 Working Set

每個 user-mode process 都有自己的 private virtual address space；kernel-mode code 則共享 system space。Virtual address 不直接等於 physical address，CPU 透過 page tables 完成轉換。這層抽象提供 isolation、稀疏配置、copy-on-write、memory-mapped file 與 paging。

Reserve、Commit 與 Resident 是三件不同的事

狀態意義常見誤解
Reserved保留一段 virtual address range不代表已配置實體頁面
Committed系統承諾提供 backing storage不代表此刻一定在 RAM
Working Set目前 resident 在 physical memory 的頁面集合被 trim 不代表 allocation 消失

VAD 描述一段位址範圍及其 protection、mapping 類型與 backing relationship；page table 則回答「這個 virtual page 目前如何轉譯」。兩者不是同一個資料結構。

Image、Mapped 與 Private

  • Image mapping：由 executable image section 支援，通常對應 EXE/DLL。
  • Mapped mapping：由 data file 或 shared section 支援。
  • Private mapping：heap、stack、一般 allocation 與 copy-on-write 後的 private page 常落在此類。

單看 RWX 或 private executable page 不能直接判定惡意。JIT compiler、相容層與某些保護器也會產生類似區域。更可靠的判斷是把 protection transition、寫入來源、thread start、call stack、signing 與 process role 結合起來。

可重複的記憶體檢查流程

  1. 確認目標 process、architecture 與 OS build。
  2. 列出 modules、mapped files 與 private regions。
  3. 找 executable private pages 或 image／disk mismatch。
  4. 檢查 region 內是否有合理 code、PE 結構或 JIT metadata。
  5. 將 active thread 的 instruction pointer 與 call stack 對回 regions。
  6. 用 timeline 驗證 allocation、write、protection change 與 execution 的先後關係。

Handle 與 Object Manager

Handle 是 process-local 的間接參照，不是全域 kernel pointer。Process 的 handle table entry 最終引用 Object Manager 管理的 object；object header 保存 type、reference count、name 與 security metadata，body 才是 file、event、process 等型別的實際內容。

這個模型解釋了幾個常見現象：

  • 相同數值的 handle 在不同 process 可指向不同 object。
  • DuplicateHandle 產生另一個 table entry，不是複製底層 object。
  • CloseHandle 移除參照；只有最後的 handle 與 kernel reference 都消失後，object 才能銷毀。
  • Named object 存在 Object Manager namespace；Win32 path 只是另一層轉譯。

System Call：邊界轉換而不是「神祕後門」

在 x64 上，ntdll 的 Native API stub 通常準備 system service number，將第一個參數從 RCX 搬到 R10，再執行 syscall。System service number 不是跨版本穩定 ABI，WOW64 路徑也不同。

SSN 隨 Windows build 變動；實務用 sig 或 Hell's Gate 動態解析，不要 hardcode。

進入 kernel mode 後，系統仍會做參數擷取、位址探測、access check 與 object reference。直接執行 system call 不會繞過 kernel security model；它最多改變某些 user-mode 觀測點。

WinDbg user-mode checklist

命令只是入口。若發現未知 thread 正在 private RX region 執行，仍應確認該 region 的建立時間、內容、calling thread、process role，以及它是否為合法 JIT。

常見誤區

  • 把 process 當排程單位：scheduler 實際排程 thread。
  • 把 virtual size 當實體 RAM：應分開看 reserve、commit、working set 與 shared pages。
  • 看到 PEB module list 就認為完整：它是 loader 維護的 user-mode view。
  • 硬背 kernel offset：跨版本與不同 symbol 會失效。
  • 把一次 syscall 當成完整行為：I/O、security、object lifetime 與 completion 可能跨多條 thread。
  • 把單一指標當 verdict：RWX、unsigned、high entropy 都需要 context。
